**Дисциплина:** Внедрение и поддержка компьютерных систем
**Форма:** индивидуальное практическое задание для ликвидации академической задолженности

## 1. Цель

Нужно было сделать LogPulse - систему из HTTP API на FastAPI, воркера и Redis.
Она принимает строки логов, проверяет их регулярками, валидные записи складывает
в Redis Stream, воркер их читает и считает статистику. Всё поднимается одним
docker compose.

## 2. Что сделано

### Парсер и регулярки

Формат строки такой:

```
<UTC ISO-8601 Z> <LEVEL> <service> <IPv4> <METHOD> <path> <status> <N>ms rid=<8 hex>
```

Разбор делает одна регулярка с именованными группами (timestamp, level,
service, ip, method, path, status, duration_ms, rid), строка проверяется целиком
через re.fullmatch, без split. Отдельно сделал ещё несколько регулярок:
TS_RE, IPV4_RE, RID_RE, PATH_RE и PROBLEM_RE (поиск WARN/ERROR). На каждую есть
свой тест.

Потом поля проверяются по типам: timestamp через datetime, IP через ipaddress,
код ответа должен попадать в 100-599, длительность в 0-600000 мс, а level/service/
method - в свои списки. Если что-то не сходится, функция кидает ParseError с
причиной, и такая строка в очередь не попадает.

Тестовый файл data/sample.log: 45 корректных строк (три сервиса, три уровня,
12 разных кодов, уникальные rid) и 6 намеренно испорченных.

**Таблица 1. Проверка регулярок и ошибок**

| Пример / тип | Ожидалось | Получилось | Пояснение |
| --- | --- | --- | --- |
| INFO auth 192.0.2.10 GET /api/login 200 12ms rid=00000001 | Разбор | Разобрана, status=200 (int) | Строка совпала с маской |
| ERROR orders ... 503 742ms rid=ee44cc22 | Разбор | Разобрана, попала в logpulse:slow | 742 больше порога 500 |

| INFO auth 999.1.1.1 ... | Ошибка IP | неверный IP: 999.1.1.1 | ipaddress не принял октет 999 |
| DEBUG auth ... | Плохой level | строка не соответствует формату | DEBUG нет в маске |
| ERROR orders ... 999 ... | Плохой статус | код ответа вне 100-599: 999 | Маску прошла, диапазон нет |

| Пустая строка (пробелы) | Отказ | пустая строка | Проверка до маски |

### Redis: очередь и статистика

Очередь сделал через Redis Stream logpulse:events. API кладёт туда события
командой XADD. Воркер читает их через XREADGROUP (группа logpulse-workers),
обновляет статистику и подтверждает через XACK.

**Таблица 2. Структуры Redis**

| Ключ | Тип | Запись / чтение | Зачем |
| --- | --- | --- | --- |
| logpulse:events | Stream | XADD / XREADGROUP, XREVRANGE | Очередь событий |
| logpulse:stats:level | Hash | HINCRBY / HGETALL | Сколько событий каждого уровня |
| logpulse:stats:service | Hash | HINCRBY / HGETALL | Сколько событий по сервисам |
| logpulse:stats:status | Hash | HINCRBY / HGETALL | Сколько ответов по кодам |
| logpulse:slow | Sorted Set | ZADD / ZREVRANGE | Рейтинг медленных (score = duration_ms, member = rid) |

Порог медленного запроса: duration_ms >= 500.

"Принято в очередь" и "обработано воркером" - это разные вещи. Принято - это
XLEN у потока, обработано - это total из /stats (сумма счётчиков уровней). После
загрузки sample.log получается XLEN = 45 и total = 45.

### FastAPI, Pydantic и ошибки

API на FastAPI: маршруты разбил по APIRouter, модели на Pydantic. Маршруты:
/health, /ingest (принимает {"lines": [...]}), /stats и /events?limit=10.
Лимиты: от 1 до 100 строк, каждая от 1 до 500 символов. Доступ к Redis идёт
через Depends, в тестах он подменяется. Ошибки: 422 на неверный запрос, 503
если Redis недоступен, все ответы в одном формате {"error": {"type", "message",
"details"}}.

**Таблица 3. Проверка API и тестов**

| Сценарий | Вход | Ожидалось | Получилось |
| --- | --- | --- | --- |
| POST /ingest | 3 валидные + 2 ошибки | accepted=3, rejected=2 | Так и есть, 2 пояснения |
| POST /ingest | sample.log (45 + 6) | accepted=45, rejected=6 | Подтверждено |
| GET /stats | после воркера | Агрегаты из Redis | total=45, уровни 15/15/15 |

### Docker Compose

Есть Dockerfile, compose.yaml и .env.example. В compose три сервиса: api,
worker, redis. Настройки идут через переменные окружения, внутри контейнеров
Redis доступен по имени redis, а не по localhost. У redis есть healthcheck, api
и worker ждут его готовности. Данные Redis лежат в volume redis-data. HTTP открыт
только на 127.0.0.1, порт redis наружу не торчит.

**Таблица 4. Журнал инцидента**

| Шаг | Действие | Ожидалось | Факт | Доказательство |
| --- | --- | --- | --- | --- |
| 1 | docker compose up --build -d | Три контейнера готовы | redis healthy, api и worker подняты | вывод docker compose ps |
| 2 | Загрузить sample.log | Статистика построена | accepted=45, rejected=6, total=45 | ответ /ingest и /stats |
| 3 | docker compose restart redis | Краткая недоступность | Воркер ждёт и повторяет попытку | строки лога воркера о повторе |
| 4 | Дождаться восстановления | Сервис снова работает | /health = 200, поток дообработан | ответ /health, XINFO GROUPS (lag=0) |
| 5 | Повторить /stats | Данные на месте | total=45, не изменилось | ответ /stats после restart |

Отдельно проверил полную остановку redis: `/health`, `/stats` и `/ingest`
возвращают 503, а после `docker compose start redis` доступность и статистика
поднимаются обратно из volume.

## 6. Инцидент с Redis

Проверял сценарий из задания: запуск, загрузка sample.log, docker compose
restart redis, ожидание и повторный /health и /stats. Дополнительно решил
проверить полную остановку redis, а не только restart.

Наткнулся на проблему: когда Redis лежит, /health не отдавал 503, а просто
висел. Сначала думал, что завис сам uvicorn. Оказалось, у клиента redis не был
задан таймаут сокета, поэтому запрос ждал ответа бесконечно. Добавил
socket_connect_timeout и socket_timeout по 2 секунды, теперь /health и /stats
быстро отдают 503.

Данные при перезапуске не теряются. Redis пишет с --appendonly yes в volume
redis-data. После restart и даже после stop/start total=45, счётчики и top_slow
остались на месте. Команду down -v для такой проверки использовать нельзя, она
удаляет volume.

При недоступном Redis приложение не падает: uvicorn продолжает работать, все
маршруты отдают 503 в общем формате, а как только Redis вернулся - снова 200.
Воркер тоже не падает: пишет в лог, что нет связи, ждёт 2 секунды и пробует
снова, после восстановления читает с того же места группы.

Про полную остановку: когда redis реально stop, а не restart,
из DNS пропадает имя сервиса, и в логе воркера появляется запись вида "нет связи
с Redis: Error -2 connecting to redis:6379. Name or service not known". Воркер её
ловит, ждёт 2 секунды и пробует снова, на работу это не влияет. При обычном
restart такого нет, потому что имя сервиса остаётся.

В итоге: сервис нормально переживает недоступность Redis, данные сохраняются,
воркер переподключается. Баг с зависанием /health был настоящий, поправил.

## 8. Ограничения

- Если сообщение придёт воркеру дважды, счётчики могут увеличиться дважды. В
  задании такие дубликаты описаны как допустимое ограничение, так что оставил
  как есть.
- Воркер один, шардирования нет.
